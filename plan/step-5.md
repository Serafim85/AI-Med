# Шаг 5 из 5 — Итоговый протокол, PDF, завершение приёма, просмотр сессий

> Этот файл самодостаточен. Его можно подавать отдельному агенту без дополнительного контекста.

---

## 1. Контекст проекта

Разрабатываем **веб-приложение — AI-ассистент врача на приеме**.

Во время приёма приложение записывает диалог врача и пациента, расшифровывает его, структурирует, предлагает диагноз и план лечения. Врач редактирует и подтверждает итоговый протокол, **после чего приложение формирует PDF, завершает приём и позволяет просмотреть сохранённые сессии**.

**Роли в MVP:** только **врач** (UI) и **пациент** (голос).

**Полный скоуп MVP (все 5 шагов):** авторизация, сессия + пациент, согласие, запись/расшифровка, структурирование + диагнозы + план, **подтверждение → PDF → завершение → просмотр сессий (этот шаг)**. **Без** интеграций, истории пациента, мобильного приложения.

## 2. Зафиксированный tech stack

**Backend:** Python 3.11+, FastAPI, SQLAlchemy 2.x async, Alembic, PostgreSQL 16, Pydantic v2, `passlib[bcrypt]`, `python-jose`.

**Frontend:** React 18 + TS, Vite, TailwindCSS, React Router v6, TanStack Query, Zustand, axios.

**PDF:** **WeasyPrint** (`weasyprint`) — основной инструмент для генерации PDF из HTML/CSS. В `Dockerfile` backend должны быть установлены системные зависимости (`libpango`, `libcairo2`, `libgdk-pixbuf-2.0-0` и т.п.).

**ASR и LLM:** уже внедрены в Шагах 3 и 4, в этом шаге не дорабатываются.

## 6. Задача ЭТОГО шага (Шаг 5)

Реализовать **финальную часть жизненного цикла сессии**:

- экран «Итоговый протокол» (сводка всего, что есть в сессии);
- подтверждение протокола врачом и переход сессии в `confirmed`;
- генерация и скачивание **PDF-протокола**;
- завершение приёма и перевод в `closed` (только просмотр);
- полноценный список сессий и просмотр ранее сохранённых сессий;
- UI-реализация сценария «Обратная связь врача по качеству рекомендаций» (UC-15, «Could») — опционально, см. 6.5.

### 6.1. Backend — финализация и PDF

**Финальный просмотр сводки:**

`GET /api/v1/sessions/{id}/summary` — сервер агрегирует и возвращает все данные для экрана «Итоговый протокол»:
```json
{
  "session": { id, patient_full_name, patient_age, patient_sex, appointment_type, status, created_at, consent_given_at, ... },
  "doctor": { id, full_name },
  "protocol": { ... полный объект protocols ... },
  "selected_diagnosis": { title, icd10_code } | null,
  "red_flags": [ { label, description, severity, acknowledged_at, doctor_note } ],
  "treatment_plan_items": [ {kind, title, details, dosage, duration, is_confirmed} ]
}
```
Сессия должна быть `analyzed` или `confirmed` или `closed`, иначе 409.

**Подтверждение протокола:**

`POST /api/v1/sessions/{id}/confirm`
- Предусловия:
  - статус сессии = `analyzed`,
  - в `protocol.final_diagnosis` не пусто,
  - нет неподтверждённых `red_flags` (все с `acknowledged_at != null`),
  - все `treatment_plan_items` либо подтверждены (`is_confirmed=true`), либо удалены.
- При несоблюдении — 422 с указанием конкретной причины (`detail: "Не выбран финальный диагноз"` и т.п.).
- Проставляет `protocol.confirmed_at = now()`, `session.status = 'confirmed'`.
- Пишет `audit_log` `action="protocol_confirmed"`.

**Генерация PDF:**

`GET /api/v1/sessions/{id}/pdf`
- Предусловие: статус `confirmed` или `closed`.
- Логика:
  1. Собрать данные как в `/summary`.
  2. Отрендерить Jinja2-шаблон `backend/app/templates/protocol.html` с подключённым CSS `protocol.css`.
  3. Передать HTML в WeasyPrint → получить PDF-байты.
  4. Ответить `application/pdf`, заголовок `Content-Disposition: attachment; filename="protocol_<session_id>.pdf"`.
- Audit `action="pdf_generated"`.

**Сервис `app/services/pdf.py`** — интерфейс:
```python
class PdfService(Protocol):
    def render_protocol_pdf(self, data: ProtocolPdfData) -> bytes: ...
```
Реализация `WeasyPrintPdfService`.

**Содержимое PDF (шаблон):**
- Шапка: название «Протокол приёма», дата, тип приёма.
- Данные пациента: ФИО, возраст, пол.
- Данные врача: ФИО.
- Жалобы, анамнез, осмотр.
- Аллергии / принимаемые препараты.
- Итоговый диагноз (название + ICD-10 если есть).
- Обработанные красные флаги (с отметкой «принято»/«отклонено» и комментарием).
- План лечения, сгруппированный по `kind` (медикаменты, обследования, рекомендации, контрольный визит).
- Подвал: «Документ сформирован AI-ассистентом и подтверждён врачом. Подпись: __________».
- Русский язык, шрифт с поддержкой кириллицы (например, DejaVu Sans — идёт в WeasyPrint из коробки).

**Завершение приёма:**

`POST /api/v1/sessions/{id}/close`
- Предусловие: статус = `confirmed`.
- Проставляет `status = 'closed'`. После этого все `PATCH`/`DELETE` эндпоинты протокола/диагнозов/плана/транскриптов должны возвращать 409. `/pdf` и `/summary` — работают.
- Audit `action="session_closed"`.

**Сохранение как черновика при выходе без подтверждения:**
- Специальный эндпоинт не нужен — если врач уходит, сессия остаётся в своём текущем статусе (`draft`/`analyzed`).
- В UI предусмотреть предупреждение (см. 6.2).

### 6.2. Frontend — экран «Итоговый протокол»

Маршрут `/app/sessions/:id/confirm` (заглушка из Шага 4 теперь наполняется).

Разделы страницы (сверху вниз) — каждый доступен только для просмотра с кнопкой «Редактировать», которая возвращает на экран анализа `/app/sessions/:id`:

1. **Шапка:** пациент, тип приёма, дата, врач.
2. **Жалобы / Анамнез / Осмотр / Аллергии / Препараты** — в виде read-only блоков.
3. **Итоговый диагноз** — название + ICD-10 (если выбран/введён). Если пусто — красная плашка «Диагноз не выбран».
4. **Красные флаги** — список с отметками «принято / отклонено», комментарий врача. Если есть необработанные — красная плашка.
5. **План лечения** — группировка по kind, у каждого пункта индикатор «подтверждён».
6. **Нижняя панель:**
   - Кнопка **«Подтвердить и сформировать PDF»** — вызывает `POST /confirm`, при успехе автоматически скачивает PDF (`GET /pdf`) и показывает диалог «Протокол подтверждён. PDF сохранён.» + кнопка **«Завершить приём»**.
   - Если `/confirm` вернул 422 — показываем подсветку конкретной причины.
   - Если сессия уже `confirmed` — кнопка «Скачать PDF» и кнопка «Завершить приём».
   - Если сессия `closed` — кнопки «Скачать PDF»; все редактирования недоступны.

**Скачивание PDF в браузере:**
- Использовать `axios` с `responseType: 'blob'`, создать временный `URL.createObjectURL`, вызвать `<a download>` клик и очистить URL.

**Предупреждение при уходе без подтверждения:**
- При попытке перейти на другой роут со статусом `analyzed` — показать диалог «Протокол не подтверждён. Сохранить как черновик?» с кнопками «Сохранить черновик» (просто переход без изменений) / «Остаться».

### 6.3. Frontend — список и просмотр сессий

На `/app` (главная) сделать полноценный список приёмов (в Шаге 3 он был базовым):

- Колонки: дата, ФИО пациента, возраст/пол, тип приёма, **статус** (бейдж: draft/recording/analyzed/confirmed/closed), итоговый диагноз (если есть), действия.
- Фильтры: по статусу (кнопки-вкладки «Все / Черновики / Подтверждённые / Закрытые»), строка поиска по ФИО пациента.
- Пагинация или infinite-scroll (`limit=20`, `offset`).
- Действия на строке:
  - «Открыть» — для `draft`/`analyzed` ведёт на соответствующий экран (запись или анализ), для `confirmed`/`closed` — на экран просмотра.
- Бэкенд должен поддерживать параметры `GET /api/v1/sessions?status=...&query=...&limit=&offset=`.

**Экран просмотра сессии** для `confirmed`/`closed`:
- Маршрут `/app/sessions/:id/view`.
- Показывает все те же блоки, что и `/confirm`, но **полностью read-only**.
- Кнопки: «Скачать PDF», «Закрыть приём» (только если `confirmed`), «Назад к списку».

### 6.4. Backend — фильтры списка сессий

Расширить `GET /api/v1/sessions` (из Шага 3):
- query params: `status` (one of enum or `all`), `query` (подстрока в `patient_full_name`, case-insensitive), `limit`, `offset`.
- Ответ: `{ items: [...], total: int }`.

### 6.5. (Опционально) Обратная связь по ИИ — UC-15

Если осталось время — добавить отметки «👍 / 👎» рядом с каждым предложением диагноза и пунктом плана:
- `POST /api/v1/feedback` — тело `{ session_id, kind: 'diagnosis'|'plan_item', ref_id, useful: bool, comment?: string }`.
- Сохранять в `audit_log` с `action="ai_feedback"` и payload'ом.
- Новая таблица не нужна.

Если времени нет — этот пункт можно опустить.

### 6.6. Тесты

Backend (`pytest`):
- `/confirm` при всех выполненных условиях → 200, статус `confirmed`, `confirmed_at` заполнен.
- `/confirm` при незавершённых red_flags → 422.
- `/confirm` без final_diagnosis → 422.
- `/pdf` для `confirmed` → content-type `application/pdf`, ненулевые байты (достаточно проверить PDF-сигнатуру `%PDF`).
- `/close` из `confirmed` → `closed`; из `analyzed` → 409.
- После `closed` любые `PATCH` протокола/плана → 409.
- Фильтр списка по `status` и `query` работает.

## 7. Definition of Done (критерии приёмки Шага 5)

1. Со страницы анализа кнопка «К итоговому протоколу» открывает новый рабочий экран со сводкой.
2. Нажатие «Подтвердить и сформировать PDF»:
   - проверяет предусловия,
   - переводит сессию в `confirmed`,
   - автоматически скачивает PDF,
   - PDF открывается в стандартном просмотрщике с корректной кириллицей и всеми блоками.
3. Нажатие «Завершить приём» переводит сессию в `closed`. После этого редактирование запрещено, просмотр и скачивание PDF доступны.
4. Попытка редактировать что-либо в `closed` сессии возвращает 409.
5. На `/app` видны все свои сессии с правильными статусами и фильтрами.
6. Экран просмотра `/app/sessions/:id/view` показывает сессию read-only для `confirmed`/`closed`.
7. При уходе со страницы `/confirm` без подтверждения — появляется предупреждение.
8. В `audit_log` появляются записи `protocol_confirmed`, `pdf_generated`, `session_closed`.
9. Все `pytest` зелёные, включая проверку PDF.
10. `docker compose up --build` по-прежнему работает; в Dockerfile backend установлены системные библиотеки WeasyPrint.
11. README дополнен разделом «Полный цикл приёма: логин → новый приём → согласие → запись → анализ → подтверждение → PDF → закрытие».

## 8. Явные ограничения этого шага

- **НЕ делаем** электронную подпись, QR-код и прочие «юридически значимые» метки — это вне MVP.
- **НЕ отправляем** PDF по email/МИС — только скачивание.
- **НЕ делаем** историю изменений протокола (аудит только через `audit_log`).
- **НЕ делаем** мультипользовательский просмотр одной сессии — только владелец.

## 9. Итог MVP

После Шага 5 приложение покрывает полный сценарий работы врача:

1. Врач входит в систему.
2. Создаёт новый приём и вводит данные пациента.
3. Фиксирует согласие пациента.
4. Ведёт запись и получает расшифровку в реальном времени.
5. Запускает анализ, получает структурированный протокол, топ-3 диагноза, красные флаги и план лечения.
6. Корректирует, выбирает диагноз, подтверждает план.
7. Подтверждает итоговый протокол, получает PDF.
8. Закрывает приём.
9. Находит прошлые сессии в списке и открывает их на просмотр.

Это и есть целевой MVP.
